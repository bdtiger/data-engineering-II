\subsection{Infrastructure Setup}

I followed the same process I used in Assignment~3 to provision and configure the VMs.
I used the OpenStack client scripts to create the VMs on Swedish Science Cloud, and Ansible playbooks
to configure them and install the required software.
I modified both the OpenStack client scripts and the Ansible playbooks from my
Assignment~3 versions to fit this assignment -- specifically, to provision a Ray cluster
instead of a Docker-based deployment and to install Ray and scikit-learn on each node.

One VM was designated the \textbf{head node}. Ray was started on it with:

\begin{lstlisting}[style=shell]
ray start --head --port=6379 \
  --node-ip-address=<head-internal-ip> \
  --dashboard-host=0.0.0.0
\end{lstlisting}

Each additional VM joined as a \textbf{worker node} by connecting to the head:

\begin{lstlisting}[style=shell]
ray start --address='<head-internal-ip>:6379' \
  --node-ip-address=<worker-internal-ip>
\end{lstlisting}

The tuning script was then executed on the head node, which distributed trials
across all connected workers via Ray's distributed scheduler and object store.
A floating IP was attached only to the head node for SSH access; inter-node
communication used the private network addresses.

  \caption{Google Colab execution of the TensorFlow distributed training tutorial
           (\texttt{MirroredStrategy}).}
  \label{fig:colab}
\end{figure}

\subsubsection{Data Parallelism vs.\ Model Parallelism}

\textbf{Data parallelism} copies the full model to every device. Each device gets a
different batch of data, computes its own gradients, and then all devices share and
average those gradients before updating the weights. TensorFlow's
\texttt{MirroredStrategy} and PyTorch's \texttt{DistributedDataParallel} both work this
way. This approach works well when the model fits on a single device and the main
bottleneck is the amount of training data. Adding more devices lets training finish
faster.

\textbf{Model parallelism} splits the model itself across devices. Different layers or
parts of the model live on different devices. This is needed when the model is too large
to fit on one device, such as very large language models with billions of parameters.
Two common ways to do this are pipeline parallelism (each device handles a group of
layers in sequence) and tensor parallelism (weight matrices are split across devices).

\textbf{When to distribute a single training run vs.\ the whole tuning sweep.}
If training one model configuration already takes too long on a single device, it makes
sense to spread that one run across multiple devices using data or model parallelism.
On the other hand, if each training run is fast, it is better to run many configurations
in parallel -- one per worker -- instead of adding communication overhead to every forward
pass. In my experiments with Ray Tune and the random forest, individual runs were fast
enough that I parallelised across configurations rather than within a single run.

\subsection{Simulation Setup}

Two \textit{Datasite} nodes were launched locally using \textbf{PySyft $\geq$ 0.8}
(\texttt{dev\_mode=True} to bypass manual approval) representing \emph{Client~A} and
\emph{Client~B}. The MNIST training set (60\,000 images) was partitioned into two
non-overlapping halves: samples 0--29\,999 sent to Client~A and samples 30\,000--59\,999
sent to Client~B.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.95\textwidth]{screenshot-pysyft-setup}
  \caption{PySyft Datasite workers (Client~A and Client~B) initialised with
           non-overlapping MNIST partitions.}
  \label{fig:pysyft-setup}
\end{figure}

\subsection{Federated Training}

A simple convolutional network was defined; its \texttt{state\_dict()} (serialised as a
plain \texttt{dict}) was submitted to each worker via a \texttt{@syft\_function}-decorated
remote function carrying an \texttt{ExactMatch} input policy and an \texttt{allow\_outputs}
output policy. Each worker performed one epoch of local SGD and returned the updated
\texttt{state\_dict}. The coordinator performed \textbf{FedAvg} -- averaging the two
returned state dictionaries by parameter tensor -- and loaded the aggregated weights back
into the global model. This procedure was repeated for five rounds.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.95\textwidth]{screenshot-federated-training}
  \caption{Terminal output showing federated training rounds, per-worker local loss, and
           FedAvg aggregation.}
  \label{fig:fl-training}
\end{figure}

\subsection{Analysis}

\subsubsection{How PySyft's \texttt{PointerTensor} / \texttt{ActionObject} Prevents
               Raw Data Access}

In PySyft~0.7 the \texttt{PointerTensor} abstraction stores only a reference (owner node
id, object id) rather than the data itself. All operations on a \texttt{PointerTensor}
(arithmetic, slicing, model forward passes) are serialised as remote procedure calls and
executed on the owning worker; only the result pointer -- not the underlying tensor values
-- is returned to the data-scientist process. The data scientist therefore never holds the
raw bytes in local memory; they interact with a \emph{proxy object} that enforces
data-locality.

In PySyft~0.8+ the equivalent mechanism is the \texttt{ActionObject}. Code that accesses
private data must be submitted as a \texttt{@syft\_function} decorated function with an
explicit \texttt{input\_policy} (governing what inputs may be passed) and an
\texttt{output\_policy} (governing what outputs may be returned). The Datasite
administrator must approve each code request before execution; in simulation mode
(\texttt{dev\_mode=True}) this approval is granted automatically. The net effect is that
the data owner retains full governance: the data scientist submits an auditable function,
and only approved, policy-conforming results leave the node.

\subsubsection{Federated Model Accuracy vs.\ Single-Worker Baseline}

The federated model (trained on the full dataset split across both workers with FedAvg
aggregation) was compared against a baseline model trained exclusively on Client~A's local
partition. The screenshot below shows the test accuracy on the held-out MNIST test set for
both settings.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.85\textwidth]{screenshot-accuracy-comparison}
  \caption{Test accuracy on MNIST: federated model (both workers, FedAvg) vs.\
           single-worker baseline (Client~A only).}
  \label{fig:accuracy}

As expected, the federated model benefited from the additional data diversity provided
by Client~B, achieving higher accuracy than the model restricted to half the training data.
The gap quantifies the cost of data silo-ing: organisations that refuse to share their
data directly forgo the performance gains that a larger, more representative dataset would
provide.

\subsection{Written Reflection}

\subsubsection{Federated Learning vs.\ Distributed ML: Statistical and System
               Heterogeneity}

Standard distributed ML (e.g.\ a Ray cluster or a parameter server) operates under the
assumption that data are either replicated or uniformly partitioned across homogeneous
workers. Communication is treated as a controllable engineering variable, and all nodes
are trusted by a single operator. Federated Learning relaxes both assumptions in critical
ways.

\textbf{Statistical heterogeneity} (\emph{non-IID data}): In FL, each client's local data
distribution reflects the behaviour of its users or sensors, which may diverge sharply from
the global distribution. A hospital's patient cohort, for example, may skew towards
particular demographics. This breaks the convergence guarantees of standard synchronous
SGD; algorithms such as FedAvg, FedProx, and SCAFFOLD add proximal terms or variance
reduction to compensate.

\textbf{System heterogeneity} (\emph{stragglers and availability}): FL clients are
consumer devices or institution servers with heterogeneous compute, memory, and
network conditions. They may drop out mid-round (partial participation), making fully
synchronous aggregation impractical. Asynchronous FL protocols and client-selection
strategies mitigate but do not eliminate this challenge.

\textbf{Relation to the Parameter Server strategy}: The Parameter Server (PS) pattern -- a
centralised store for model parameters that workers push gradients to and pull updates
from -- is the architectural ancestor of the FL aggregation server. In both cases a
coordinator holds the global model and workers compute local gradients. The key
differences are (i) the PS assumes trusted workers on a private network with predictable
latency, while the FL server treats clients as potentially unreliable and untrusted;
(ii) FL must contend with non-IID data and privacy constraints that are irrelevant in
traditional PS deployments; and (iii) FL aggregation (FedAvg) operates on full local
model updates rather than mini-batch gradients, reducing communication frequency at the
cost of potential client drift.
